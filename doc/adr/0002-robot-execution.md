# Robot execution, permissions and persistence

2026-11-05 extension: Settings → Providers reads T3 Code's local configured instances and cached model lists. The user authorized connection and native execution together. Orbit launches native executables directly, reusing account directories and configured credential environment only in memory. T3 Code itself is not a runtime dependency. SHA-256 connection fingerprints prevent existing conversation references from silently switching accounts after T3 settings change.

Native execution asks for one command-scoped permission before process launch, explicitly covering the native agent's file/program/network access and its configured MCP servers. This is the actual broad scope, not an individual-action guarantee. Native requests that follow still require conversation-bound approval and never select permanent grants. Cancellation kills the process group; effects already completed remain. Orbit local tools keep exact-action approval. Orbit-profile MCP allow-lists are not widened for native agents: unsupported attachments stop with an error. Native stdout is bounded, private reasoning is omitted and known configured credential values are redacted. All approvals remain memory-only and imports do not replay work.

The user authorized implementation on 2026-11-03. Robots are independent of the single-question AI Prefix. Orbit owns the runtime; it does not spawn Codex or T3 Code to execute commands.

Use the existing SQLite dependency for a separate `robots.db`. Store Roles, Robot profiles, conversations and ordered activity in separate tables. Keep conversation bodies out of `config.json` and out of launcher show/hide work. History queries return 50 summaries at a time; opening a conversation reads its entries. The storage API must run on a worker, as existing Orbit storage does.

Creating a conversation transactionally copies its model, provider, Role instructions and project path and records the first command. Later profile or Role edits apply to new conversations. Existing conversations retain their context. Titles use the first nonempty message line, limited to 80 grapheme clusters so Arabic and joined emoji survive intact. Activity updates history order; ratings accept integers from one to five. Deleting a conversation cascades to its activity. SQLite secure deletion clears deleted cell contents; separately retained backups are not erased.

The runtime has one worker for one executing Robot and queued commands. Hiding the launcher must not cancel work. A local file or shell operation must pause for approval of the exact operation and its arguments, including the working directory. Project paths do not sandbox access. Denied or stale approvals must cause no execution. Persisted tool activity is evidence only; it must never become reusable execution authority, including after restart or import. Interrupted operations must not replay automatically because an external side effect may already have happened.

Installed Skills supply instructions, not permission. They execute through Orbit's own local and MCP tools. Unsupported Codex/T3-specific operations must be reported rather than silently treated as executed. Built-in internet research must work independently of the selected model provider and preserve source URLs. Writing a requested Markdown report remains a local write requiring approval.

Users explicitly enable MCP tools. Those calls then run automatically, including machine access the MCP server exposes. Local stdio server configuration stores an executable and separate arguments. Secret environment fields contain only OS keyring entry identifiers. Provider keys also remain in the existing OS keyring. The runtime must redact credentials before recording tool activity; users must not place secret values in arguments or ordinary conversation text.

Backup version 2 introduced a validated logical Robot snapshot; version 3 also records queued-command states. Read all Robot tables in one SQLite transaction rather than copying an open database. Import validates before replacing data and restores the database inside the existing staging directory; failures retain the old profile. Imported MCP enabled-tool lists are cleared, while configuration, credential references, conversation snapshots, activity and ratings survive. Import never reads, writes or deletes OS keyring values. Backup version 1 remains readable and contains no Robot data. Previous data retained by the existing import mechanism remains available for recovery.

Step 2 supplies worker-side local, Skill, MCP and search tools. Approval requests retain the exact action, absolute path or program/argument vector, and canonical project directory. IDs are unique within the process across conversation workers. Resolution consumes the pending request before execution, even on failure; denial and cancellation discard it. These objects are never serialized. The runtime must keep each approval bound to its owning conversation and discard pending requests on restart. Shell scripts are explicit program calls (for example `/bin/sh` with separate arguments); Orbit never builds shell text from a path or tool argument.

Local text and captured stdout/stderr are limited to 1 MiB each. Writes use a new sibling temporary file, sync and rename, preserving existing permissions. Commands time out after 60 seconds and terminate their process group on Linux or process tree on Windows. Timeout does not roll back side effects; explicitly detached descendants may survive. The UI must show this permission scope, and runtime must never retry uncertain actions automatically. Skill loading is an approved UTF-8 read of a selected installed `SKILL.md`; relative resource paths retain that Skill's directory. Only instruction workflows using Orbit local and enabled MCP tools are supported. Runtime dispatch must reject unsupported Codex/T3 operations with an actionable error; loading a Skill does not execute it or authorize its resources.

MCP implements the [2025-06-18 stdio transport](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports) and initialization handshake. Discovery follows bounded pagination. Individual messages and the complete discovered tool list are limited to 1 MiB; requests have 60-second deadlines. Sampling, roots and elicitation are not advertised; server requests receive an unsupported-method error. Changed configuration requires reconnection, and every call checks the current enabled-tool list. Failed sessions close without replay. Discovery launches the configured program: it is allowed by explicit configuration/discovery or a submitted command with enabled tools on that server. Disabled servers are never started by the runtime.

MCP receives only a minimal standard environment plus explicitly configured secret variables. Secret references are read from service `orbit-robots` in the OS keyring. Stderr is discarded; returned strings, object keys and JSON-RPC errors redact those secret values before leaving the session. The runtime must also apply the session's redaction to request arguments before storing tool activity. This protects literal configured values, not arbitrary encoded secrets or secret files deliberately read by an approved full-access tool.

Built-in research uses the [Brave Search web endpoint](https://api-dashboard.search.brave.com/app/documentation/web-search/get-started), independently of Ollama/OpenAI/Gemini. It needs the `brave-search` keyring entry in `orbit-robots`; no credential is added to profile data or backups. Search has a 30-second deadline, a 1 MiB response cap, no redirects, and returns up to ten titles, snippets and original HTTP(S) source URLs. Missing credentials give a configuration error. The runtime uses those links when composing a requested Markdown report and asks for local-write approval before saving it. Reading full pages can use an enabled MCP tool.

Step 3 records Queued and Run entries in the conversation. The new entry variants require robots.db schema 2 and backup version 3; schema 1 migrates without changing its tables or existing records. Queued work is persisted before acceptance, and only the command selected for execution enters model context. First use after restart marks unfinished work Interrupted without executing it. Ordinary completion and failure are durable; a storage failure stops further execution. Historical approval records cannot recreate live pending actions.

One runtime Handle belongs to the daemon/workbench integration. Its worker is independent of window visibility and continues if an observer disconnects. It starts lazily on the first request. A global FIFO preserves each Robot's submission order and prevents simultaneous work by different profiles. An approval pauses that worker, while it can still accept or cancel queued commands. Cancelling is checked before and after provider calls and before each tool; already approved calls may finish or time out. Pending actions disappear when their command ends. The worker records intent again after approval, before executing, so deletion or a failed history write while waiting prevents the action.

Use each provider's native tool protocol. OpenAI Responses retains encrypted reasoning items during one command with store=false; Gemini preserves thought signatures; Ollama requires native tool support. Provider continuation data is transient. New commands reconstruct textual history and completed tool results, retaining the conversation's stored context rather than current Role/model settings. Untrusted tool content cannot authorize execution. Selected Skills are loaded through approvals before model work; denial stops the workflow. Unsupported tool operations produce an error, and uncertain failed actions are not replayed automatically.

Limits are explicit: 128 queued commands, 32 model turns per command, 16 tool calls per turn, 8 MiB per model request and 512 KiB per ordinary saved tool result with a truncation notice. Selected Skills retain their existing full 1 MiB allowance. Provider requests retain the existing 120-second deadline. Enabled MCP settings are rechecked before calls. Known provider and connected MCP credential values are redacted from visible model/tool output and saved tool arguments; arbitrary secrets intentionally pasted into commands or read from files remain outside that literal-value protection.

The workbench consumes runtime events, exposes approvals and cancellation, and keeps its Handle alive while hidden. Import coordination stops the idle runtime and closes its database before the directory swap; imported commands never gain replay authority.

The workbench bridge performs profile, Role, MCP discovery and history I/O off the UI thread. It owns one runtime while the launcher is hidden. Approval clicks carry the displayed conversation ID and action ID; changing selection cannot retarget approval. The bridge tracks submitted runs until acceptance/rejection/completion, and rejected submissions identify their run separately from general errors. Conversation deletion is disabled until all its work finishes. Import rejects outstanding work, synchronously shuts down an idle runtime and closes its database, and excludes new work until the directory replacement completes. Future use opens the imported database and marks unfinished work Interrupted, without replay.
